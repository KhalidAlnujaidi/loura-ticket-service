Loura — ticket classification service

A small HTTP service that ingests support tickets, classifies each one through a model treated as an unreliable dependency that returns text, and serves the results back with filters and pagination.

Take-home brief·4–6 h budget·Python · FastAPI · SQLite·4 endpoints·37 tests·0 API keys

01 What was built

POST /tickets→ row: pending→ asyncio queue→ worker ×2→ model call (text)→ validation gate→ classified | retry | failed

SQLite is the source of truth. The queue is deliberately disposable — it is rebuilt from pending rows on every boot.

  • API — 4 endpoints: create (201; 200 on duplicate id, never re-classified), get, filtered + paginated list, reclassify (202).
  • Store — one SQLite file with CHECK constraints on status / category / priority, so invalid states cannot land even from a future code path.
  • Worker — in-process asyncio queue + 2 loops; at-least-once recovery, nothing lost on restart.
  • Boundary — every model response passes one validated choke point before anything is stored (§05).
  • Backends — Laya (default; local typed-decision model, no API keys) and FakeLLM (deterministic, scriptable: invalid JSON, bad enums, exceptions, delays, injection mode).

02 Steps taken

  1. Plan before code. Wrote the implementation plan and answered the brief's open questions first — a 4–6 h budget forces clarity over feature count, and every later choice traces back to that document.
  2. Chose a stack with the fewest moving parts. FastAPI + Pydantic v2 (strict validation is the whole theme), SQLite (zero-ops, ACID), in-process asyncio (no broker to install), no API keys, no Docker.
  3. Settled the deliberately-open questions before writing the worker. Storage, execution model, concurrency, restart semantics, retry policy, injection handling and validation-failure outcome determine the schema and the worker's state machine — so they were decided up front, then documented with their trade-offs.
  4. Built in dependency order. config → schemas → db → prompts → the model boundary → worker → routes + lifespan → seed → tests. The boundary came before the API because every other part hinges on it.
  5. Spiked the real model, then integrated it. Laya was measured against all 10 appendix tickets before being adopted: 8/10 zero-shot category agreement, ≈206 ms median on CPU, immune to the injected ticket. It shipped behind the same complete() contract — first as an optional backend, then as the default per request. FakeLLM stayed for deterministic tests and slim installs.
  6. Audited the whole thing (A–Z QA). Full source read, live server driven over real HTTP, ≈180 adversarial assertions. Six findings — all in config validation and process lifecycle. The sharpest: LOURA_WORKERS=0 produced zero worker loops, so the API answered 201, looked healthy, and classified nothing, silently. Fixed by range-checking every numeric override at parse time (fail at startup, never degrade quietly) plus an idempotent worker start, each with regression tests.
  7. Verified from a clean clone. Cloned the commit into a fresh directory and reproduced the suite, the config guard, a live boot and the seed — so the submission is self-contained, not an artifact of local state. The test suite grew from 16 + 1 to 36 + 1 during the hardening pass.

03 Decisions and why

Open questionDecisionWhy / trade-off
StorageSingle SQLite fileACID, zero ops, and the source of truth for recovery. Trade-off: sync driver on the event loop; Postgres + async driver at scale.
Async executionIn-process asyncio queueNo broker to install. The boundary that matters (recovery) lives in the DB, not in broker acknowledgements.
Concurrency2 workers, env-tunableEnough to show overlapping classification; gentle on a provider rate limit.
RestartAt-least-once, nothing lostCancelled in-flight calls never write; attempt counters increment only when an attempt finishes, so the row stays pending and re-runs on boot. A duplicate run costs inference, not correctness.
Retry policy3 attempts, jittered backoffCovers malformed JSON, bad enums, schema violations, exceptions, timeouts. Then failed + reason — the raw invalid output is logged, never persisted.
Prompt injectionEscape, never trustTicket text never enters the system prompt; it is XML-escaped inside <ticket> tags, and the output is hard-validated. Residual semantic risk is documented and demonstrated by a test, not hidden.
Validation failureRetry, then failSame path as any other model error; garbage never becomes a classification.
Serving modelLaya default, FakeLLM for testsLaya is local, typed-choice and key-free; both implement the same complete() contract, so retries, timeouts, recovery and storage are backend-agnostic.

04 Evidence

  • Test suite — 36 passed + 1 skipped on the slim install; 37 passed with the real-model e2e. Suites cover API ingest, classification failure modes, injection, restart recovery, and config/lifecycle.
  • Fresh clone — suite, config guard, live boot and seed all reproduced in a clean directory.
  • QA probes — ≈180 adversarial assertions: API boundary 30/30, model-boundary fuzz 21/21 (no unexpected exception types), crash windows genuinely safe, 40 tickets across 8 workers classified exactly once. Zero correctness failures in the core pipeline.
  • Classifier agreement (10 appendix tickets, per backend) — Laya 8/10 zero-shot, ≈206 ms median CPU; FakeLLM 9/10. They miss different tickets: they are different backends, not competing accuracy claims.

05 The model boundary

Everything the worker believes about the model passes through one gate, whichever backend serves:

raw text → extract JSON  (raw / ``` fences / first balanced {…})
         → strict Pydantic  (Literal enums · summary 1–300 · extra=forbid)
         → store | reject(reason) → retry | failed

Failure reasons: invalid model output: …, llm error: Type: …, llm timeout after Xs. Honest limit: schema validation guarantees shape, not truth.

06 Honest weaknesses

  • Semantic injection is not solved — a test deliberately proves that a willfully compliant model's injected-but-schema-valid output still gets stored. Shape is guaranteed; truth is not.
  • The default backend's summary is templated, not generated (Laya is non-generative). Safe and honest — it never quotes untrusted text — but bland.
  • Heavy default install — torch plus an ≈808 MB checkpoint, downloaded once on first boot. make install-slim + LOURA_LLM_BACKEND=fake is the light path.
  • Synchronous sqlite3 on the event loop — fine at this scale, wrong at volume; single-node only.
  • Zero-shot priority is the weak primitive — t-1003 ("production… blocking") came back medium from the stock checkpoint.
  • No auth, no rate limiting, no durable broker — named as out of scope rather than pretended.
